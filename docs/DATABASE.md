# FeedCasket Database Specification

## 1. Purpose

This document defines the relational data model for FeedCasket.

The database uses **Cloudflare D1**.

D1 is the durable application database for FeedCasket.

The database must store product/business data, not transient rate-limit events.

The schema must support:

* Developer accounts
* Projects
* Allowed domains
* Feedback
* Screenshot metadata
* Feedback status
* Usage/credits
* Future purchased credits
* Multi-tenant ownership
* Search
* Auditable relationships

The schema should remain intentionally small.

Do not create tables for speculative future features.

---

# 2. Database Technology

Use:

* Cloudflare D1
* SQLite-compatible SQL
* Foreign key constraints
* Appropriate indexes
* Version-controlled migrations

Database schema changes must be represented by migration files in the repository.

Never make undocumented schema changes directly in production.

---

# 3. ID Strategy

Application entities should use opaque IDs rather than exposing sequential database identifiers where practical.

Use text-based IDs generated by the application for externally meaningful resources.

Examples:

```text
user_id
project_id
feedback_id
credit_transaction_id
```

The public project identifier must be separate from the internal project primary key.

This separation is important because:

```text
internal project ID
≠
public project identifier
```

The public identifier is intended for customer-side integration.

The internal database ID is an internal application identifier.

---

# 4. Timestamp Strategy

All durable timestamps should be stored consistently.

Use UTC.

Recommended format:

```text
ISO 8601 / UTC
```

Example:

```text
2026-09-23T12:00:00.000Z
```

Server-side timestamps should be authoritative for important events.

Do not trust a visitor-supplied timestamp as the official submission time.

---

# 5. Entity Relationship Overview

The core ownership structure is:

```text id="z4qg6p"
User
 │
 ├── Project
 │      │
 │      ├── Project Domains
 │      │
 │      ├── Feedback
 │      │      │
 │      │      └── Screenshot metadata
 │      │
 │      └── Usage/Credits
 │             │
 │             └── Credit Transactions
 │
 └── Account-level settings
```

The most important authorization path is:

```text id="d4t3nq"
Authenticated User
       ↓
Project
       ↓
Feedback
```

Every private feedback query must be able to establish this ownership relationship.

---

# 6. users

Represents a FeedCasket developer account.

The exact authentication provider is not fixed by this database specification.

Authentication credentials/secrets should be managed by the chosen authentication system rather than stored as plaintext database fields.

## Fields

```text
id
email
auth_subject
created_at
updated_at
```

### id

Internal user identifier.

* Primary key
* Opaque application ID

### email

Developer's account email.

* Required
* Unique
* Normalized for consistency

### auth_subject

Identifier linking the application user to the selected authentication system.

Examples may include an authentication-provider user ID.

* Required once authentication is implemented
* Unique

The application must not assume a specific authentication provider inside the database schema unless that provider is explicitly selected later.

### created_at

Account creation timestamp.

### updated_at

Last account record update timestamp.

---

# 7. projects

Represents a developer's website/application integration.

## Fields

```text
id
user_id
name
website_url
public_identifier
status
created_at
updated_at
```

### id

Internal project ID.

* Primary key
* Opaque application ID

### user_id

Owner of the project.

* Required
* Foreign key → users.id

A project must always belong to one developer account.

### name

Developer-defined project name.

Example:

```text
My SaaS
```

### website_url

Primary website URL supplied by the developer.

It should be validated by the application before storage.

### public_identifier

The identifier used by the customer's website/API integration.

Requirements:

* Required
* Unique
* Non-secret
* Not used as dashboard authorization

Example:

```text
fc_abc123...
```

The final format may be selected during implementation.

### status

Initial possible values:

```text
active
disabled
```

This allows the API to stop accepting feedback for a disabled project without deleting its historical data.

### created_at

Project creation timestamp.

### updated_at

Last project modification timestamp.

---

# 8. Project Ownership

A project must always belong to the authenticated user through:

```text
projects.user_id → users.id
```

Every private project operation must verify ownership.

Examples:

```text
GET project
PATCH project
GET feedback
PATCH feedback
GET usage
GET screenshot
```

must all check the authenticated developer's ownership path.

---

# 9. project_domains

Stores the domains allowed to submit feedback for a project.

Do not store the domain list as an unstructured JSON blob unless there is a clear implementation reason.

A separate relational table keeps domain validation explicit and searchable.

## Fields

```text
id
project_id
domain
created_at
```

### id

Internal domain-record ID.

### project_id

Owning project.

* Foreign key → projects.id

### domain

Normalized allowed domain.

Examples:

```text
example.com
www.example.com
app.example.com
```

Do not store URL schemes in this field.

The implementation should normalize domains consistently before comparison.

### created_at

Creation timestamp.

---

# 10. Domain Rules

A project may have multiple allowed domains.

Example:

```text
Project
 ├── example.com
 ├── www.example.com
 └── app.example.com
```

A request should be compared against the project's configured domains according to the application's origin/domain validation rules.

Domain validation is an abuse-control mechanism.

It is not authentication.

---

# 11. feedback

Represents one visitor feedback submission.

## Fields

```text
id
project_id
submission_id
message
visitor_email
page_url
page_title
user_agent
device_type
device_info
viewport_width
viewport_height
screen_width
screen_height
screenshot_id
status
created_at
```

Not every field must necessarily be populated.

---

# 12. feedback.id

Internal feedback identifier.

* Primary key
* Opaque application ID

It may be exposed to the authenticated dashboard/API where appropriate.

It must not grant access by itself.

---

# 13. feedback.project_id

Identifies the project receiving the feedback.

* Required
* Foreign key → projects.id

Every feedback record must belong to exactly one project.

---

# 14. feedback.submission_id

Client-generated or server-coordinated identifier used to help prevent accidental duplicate submissions caused by retries.

Requirements:

* Unique within the appropriate project scope
* Indexed/unique as appropriate
* Must not be treated as an authentication credential

The exact idempotency strategy is defined by the API implementation.

---

# 15. feedback.message

The actual visitor feedback.

Requirements:

* Required
* Non-empty after trimming
* Maximum length enforced by application logic
* Stored as untrusted text
* Never rendered as raw executable HTML

The database should not rely solely on frontend validation.

---

# 16. feedback.visitor_email

Optional visitor email address.

Requirements:

* Nullable
* Validated before storage
* Maximum length enforced
* Stored only when supplied

The visitor does not need a FeedCasket account.

---

# 17. feedback.page_url

Optional page URL where the feedback originated.

Requirements:

* Nullable
* Maximum length
* Treated as untrusted input

The dashboard may display it as a link only after safe URL handling.

---

# 18. feedback.page_title

Optional page title.

Requirements:

* Nullable
* Maximum length
* Treated as untrusted text

---

# 19. feedback.user_agent

The browser user-agent observed by the Worker.

Where available, this should come from the server-side request headers rather than being trusted from a browser-provided custom field.

Requirements:

* Nullable
* Length-limited
* Stored only because it provides useful feedback context

---

# 20. feedback.device_type

Optional normalized device classification.

Possible examples:

```text
desktop
tablet
mobile
unknown
```

This field is optional.

Do not build a complicated device-detection system merely for this field.

---

# 21. feedback.device_info

Optional basic device metadata.

If used, it should contain only information justified by the product.

Do not store unnecessary browser/device information simply because it is available.

If structured information is required, it may be stored in JSON text using the database's supported JSON capabilities.

Avoid turning this field into an uncontrolled collection of arbitrary request data.

---

# 22. Viewport and Screen Fields

Optional numeric fields:

```text
viewport_width
viewport_height
screen_width
screen_height
```

The application should validate reasonable bounds.

Do not trust these values for security decisions.

They are informational metadata only.

---

# 23. Screenshot Metadata

The feedback table should reference screenshot metadata rather than storing binary image data.

A screenshot should not be stored directly inside the D1 database as a large binary value.

The actual image belongs in R2.

---

# 24. screenshots

Represents metadata for a screenshot stored in R2.

## Fields

```text
id
feedback_id
object_key
original_filename
content_type
size_bytes
created_at
```

### id

Screenshot metadata identifier.

### feedback_id

Feedback associated with the screenshot.

* Foreign key → feedback.id
* Appropriate uniqueness should enforce the initial product rule of at most one screenshot per feedback unless later expanded.

### object_key

The R2 object key.

This is an internal storage reference.

Do not expose it as an unrestricted public storage credential.

### original_filename

Optional original filename.

It is for informational purposes only.

Do not trust it for object storage paths.

### content_type

Validated MIME/content type.

Examples:

```text
image/png
image/jpeg
image/webp
```

The final allowed list is an application/security decision.

### size_bytes

Actual accepted file size.

The server should determine this rather than blindly trusting a client-provided value.

### created_at

Upload/storage timestamp.

---

# 25. feedback.status

Initial values:

```text
unread
read
```

This is the MVP feedback workflow.

Do not introduce statuses such as:

```text
planned
in_progress
resolved
closed
```

unless a future product requirement specifically calls for them.

---

# 26. usage / Credit Model

FeedCasket needs to distinguish:

1. Capacity included by the product/free allowance.
2. Capacity purchased later.
3. Capacity actually consumed.

The model should allow this without requiring payment processing during the first implementation.

---

# 27. project_usage

Represents the current usage/balance state for one project.

## Fields

```text
project_id
included_credits
purchased_credits
used_credits
created_at
updated_at
```

### project_id

Primary key and foreign key → projects.id.

There should be one current usage record per project.

### included_credits

Capacity granted by the free/product allowance.

### purchased_credits

Additional capacity purchased later.

For the initial MVP this can remain zero.

### used_credits

Number of accepted feedback submissions counted against the project's allowance.

### created_at

Usage record creation timestamp.

### updated_at

Last usage modification timestamp.

---

# 28. Available Capacity

Conceptually:

```text
available =
included_credits
+
purchased_credits
-
used_credits
```

The exact implementation must use safe numeric handling and server-side validation.

A project with no remaining capacity must not accept a new feedback submission.

---

# 29. Concurrent Usage

Usage enforcement is security/business-critical.

Do not implement:

```text
SELECT remaining
↓
if remaining > 0
↓
INSERT feedback
↓
UPDATE usage
```

as an unsafe sequence where simultaneous requests can both observe the same remaining capacity.

The implementation must use a transaction/atomic database operation or another concurrency-safe mechanism so accepted submissions cannot trivially exceed the project's available capacity.

---

# 30. credit_transactions

A transaction/history table should exist so future purchased credits and other allocations can be audited without relying only on a mutable balance.

## Fields

```text
id
project_id
type
amount
reference
created_at
```

### type

Initial conceptual values:

```text
free_allocation
purchase
adjustment
usage
refund
```

The exact allowed set can be refined during implementation.

### amount

Signed or otherwise consistently defined quantity.

The implementation must choose one convention and document it.

### reference

Optional reference to an external event.

Examples:

```text
initial_free_allocation
payment_provider_transaction_id
admin_adjustment_reference
```

Do not require payment-provider data during the initial MVP.

---

# 31. Usage Ledger vs Current Balance

The application may maintain both:

```text
project_usage
```

and:

```text
credit_transactions
```

The purpose is different.

### project_usage

Fast current-state lookup.

### credit_transactions

Auditable history.

The application must keep them consistent.

A future reconciliation process may compare them if required.

---

# 32. Account Settings

Do not create a large generic settings table for the MVP.

Only persist settings that actually exist.

Potential future account/project settings may include:

* Notification preferences
* Retention settings
* UI/integration configuration

These should be added only when the corresponding feature is actually implemented.

---

# 33. Email Reply Data

The Gmail/email-compose reply feature does NOT require storing a separate email-message table for the MVP.

The necessary information already exists on feedback:

```text
visitor_email
message
page_url
created_at
```

The dashboard can construct the email composition client-side.

Do not create an email-sending subsystem merely for this feature.

---

# 34. Notification Data

Actual automated email notifications are not part of the initial reply mechanism.

If future product requirements introduce transactional notifications, introduce the required notification schema at that time.

Do not create unnecessary notification tables now.

---

# 35. Recommended Foreign Keys

The core relationships should use foreign keys.

Conceptually:

```text
projects.user_id
    → users.id

project_domains.project_id
    → projects.id

feedback.project_id
    → projects.id

screenshots.feedback_id
    → feedback.id

project_usage.project_id
    → projects.id

credit_transactions.project_id
    → projects.id
```

Use appropriate deletion behavior deliberately.

Do not use cascading deletes everywhere without considering whether historical feedback or credit records should survive an account/project deletion.

---

# 36. Deletion Policy

The MVP does not require immediate permanent deletion workflows.

Do not implement destructive cascading deletion simply because it is convenient.

Before implementing account/project deletion, decide:

* Whether feedback is deleted
* Whether screenshots are deleted
* Whether usage history is retained
* Whether credit history is retained
* Whether recovery is possible
* Required privacy/data-retention behavior

Until that policy exists, destructive deletion should not be exposed casually.

---

# 37. Index Strategy

Create indexes for common lookup paths.

At minimum, consider indexes for:

```text
projects.user_id
projects.public_identifier
project_domains.project_id
project_domains.domain
feedback.project_id
feedback.project_id + feedback.created_at
feedback.project_id + feedback.status
feedback.submission_id
credit_transactions.project_id
```

The exact indexes should be chosen based on actual query patterns.

Do not create dozens of speculative indexes.

Indexes have performance and storage implications, so every index should support a real query or uniqueness requirement.

---

# 38. Search Strategy

MVP search should begin with D1/SQLite capabilities.

Search targets:

* feedback.message
* feedback.visitor_email
* feedback.page_url
* feedback.page_title

Do not introduce a dedicated search service for the MVP.

If search scale later justifies full-text search, evaluate D1's supported SQLite/FTS capabilities before adding external infrastructure.

---

# 39. Data Integrity

Use database constraints where they provide genuine protection.

Examples:

* NOT NULL
* UNIQUE
* FOREIGN KEY
* reasonable CHECK constraints

Do not rely entirely on application code for relationships that the database can safely enforce.

---

# 40. Multi-Tenant Isolation

The database model must make tenant ownership explicit.

For example:

```text
User A
 └── Project A
       └── Feedback A

User B
 └── Project B
       └── Feedback B
```

A private dashboard query must always be able to constrain results to the authenticated user's ownership.

A safe query pattern conceptually looks like:

```text
feedback
JOIN projects
ON feedback.project_id = projects.id
WHERE projects.user_id = authenticated_user
```

Do not query private feedback solely by feedback ID.

---

# 41. Public vs Private IDs

The following may be exposed to customer-side code:

```text
project.public_identifier
```

The following are private application data:

```text
authentication/session information
database credentials
Cloudflare credentials
internal storage credentials
privileged service credentials
```

Knowing a public project identifier must not reveal:

* Dashboard data
* Feedback records
* Usage information
* Screenshots
* Account information

---

# 42. Migration Structure

Database schema changes must be version-controlled.

A suitable structure may be:

```text
migrations/
├── 0001_initial_schema.sql
├── 0002_add_indexes.sql
└── ...
```

The exact filenames are implementation details.

Every new schema change should create a new migration rather than modifying an already-applied migration.

---

# 43. Initial Schema Goal

The first database migration should establish only the actual MVP foundation.

The initial schema should cover approximately:

```text
users
projects
project_domains
feedback
screenshots
project_usage
credit_transactions
```

Do not add speculative tables for:

* teams
* organizations
* AI processing
* integrations
* analytics
* referrals
* advanced workflows
* billing subscriptions

unless the corresponding feature becomes part of the implemented MVP.

---

# 44. Database Completion Criteria

The database implementation is complete for the MVP when:

1. Users can be represented safely.
2. Projects belong to users.
3. Projects have unique public identifiers.
4. Projects can have allowed domains.
5. Feedback belongs to projects.
6. Feedback supports the required fields.
7. Screenshots can be represented and linked to feedback.
8. Screenshot binaries remain in R2 rather than D1.
9. Read/unread state persists.
10. Usage can be tracked.
11. Credit history can support future purchased capacity.
12. Foreign-key relationships protect data integrity.
13. Indexes support the actual dashboard/API queries.
14. Migrations can reproduce the schema.
15. Multi-tenant ownership can be enforced through the schema and backend queries.

---

# 45. Implementation Rule

This document defines the intended data model.

Jules should not create additional persistent entities merely because they seem architecturally interesting.

When implementation reveals a genuine requirement for another table or a different relationship, document the reason and update this specification before introducing unnecessary schema complexity.

The database should remain small, explicit, and directly connected to FeedCasket's actual product behavior.
